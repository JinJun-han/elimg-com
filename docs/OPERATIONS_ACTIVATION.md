# ELIMG 운영실 1차 구현

## 범위

원본 elimg-com Worker에 /ops/와 /api/ops/*를 추가했습니다. 공개 홈페이지와 기존 API는 유지합니다.
관리자 한 명이 사업·교육, 비자브릿지, 상담·돌봄, 선교·네트워크를 관리하는 구조입니다.
접수 등록 → 긴급 표현 표시 → 다음 행동·회신 초안 생성 → 검토·진행·완료 처리를 제공합니다.
자동 초안은 규칙 기반이며 생성형 AI가 아닙니다. 외부 AI 전송·자동 메시지 발송은 구현하지 않았습니다.

## 현재 상태

- 로컬 검증용. 운영 배포·DNS 변경·새 저장소 생성·유료 가입은 하지 않았습니다.
- /ops/?demo=1은 가상 예시이며 새로고침하면 초기화됩니다. 개인정보를 입력하지 마십시오.
- 실제 모드는 OPS_ENABLED=true와 32자 이상의 무작위 OPS_OWNER_KEY가 모두 설정되어야 열립니다. 기존 ADMIN_KEY는 운영실 로그인에 사용하지 않습니다.
- OPS_BUSINESS, OPS_VISA, OPS_CARE, OPS_MISSION에 각각 별도의 KV namespace를 바인딩해야 합니다.
- 기존 FEEDBACK 저장소를 재사용하지 않습니다. 누락된 바인딩은 저장 성공처럼 표시하지 않고 503을 반환합니다.
- elimg.com /api/lead 수집은 원본 저장 성공 후 운영실로 자동 연결합니다. Netlify 양식과 과거 백업 파일은 아직 이관하지 않습니다.
- 현재 담당자는 owner 한 명입니다. 향후 담당자 권한은 별도 설계가 필요합니다.

## 운영 활성화 전 확인

1. 현재 운영 소스·배포 버전·DNS·설정·운영 데이터 백업 및 별도 환경 복구 검증.
2. 새 KV namespace 4개의 목적·보관 범위와 무료 사용량 한도 확인. 비밀값은 저장소에 커밋하지 않음.
3. OPS_OWNER_KEY를 주인님만 보관하는 무작위 비밀값으로 설정하고 공유하지 않음. 인증은 키 소지 증명이며 실명/이메일 계정 확인은 아님. 로그인 시도 제한 및 별도 계정 인증은 운영 전 점검. HMAC 서명 쿠키는 1시간 후 만료.
4. 운영실 전용 OPS_OWNER_KEY는 기존 ADMIN_KEY와 독립. 전용 키 회전은 운영실 세션을 무효화함. 로그아웃은 현재 브라우저의 쿠키를 지우며, 복사된 토큰을 서버에서 개별 철회하는 기능은 없음.
5. Cloudflare KV는 eventual consistency이며 트랜잭션·동시 수정 충돌 검사가 없습니다. 단독 운영 범위에서만 사용.
6. 운영실 상태 변경·접수 생성 이후 일시적인 읽기 지연을 수용할지 결정. 쓰기 오류 후 무조건 재시도하면 중복될 수 있음.
7. 원본 FEEDBACK에 남은 lead_ 신청은 운영실의 상담 신청 연동 버튼으로 50건씩 재처리합니다. 문의 유형이 명확한 요청만 목적별로 복사하고, 모호한 요청은 원본에 남겨 소유자가 확인해야 합니다.
8. 업무별 데이터 보관·삭제 정책 확정. 이 1차 화면에는 삭제 기능이 없습니다.
9. 사용자에게 변경안과 복구 검증 결과를 보여주고 명시적 배포 승인을 받은 후 활성화.

## 검증

`node --test tests/operations.test.mjs tests/lead-bridge.test.mjs tests/contact-intake.test.mjs`

인증 차단, 위조 쿠키, 교차 사이트 요청 차단, 업무별 저장소 분리, 생성·상태 변경, 페이지네이션,
설정 누락, 삭제 거부 및 기존 라우팅 보존을 메모리 KV로 확인합니다. 실제 Cloudflare 저장·복원 검증을 대체하지 않습니다.

## 배포·복구

승인 후 분리된 검증 환경에서 시작합니다. 자동 배포가 켜진 main에는 승인 전 푸시하지 않습니다.
이전 배포 버전과 환경 바인딩을 기록하고, 기능 중단 시 OPS_ENABLED를 끄면 신규 운영실 API가 차단됩니다.
이는 즉시 차단 방법일 뿐 기존 데이터 백업·삭제·완전 복구를 대신하지 않습니다.

## 소유자 전용 화면 보호

- /ops/login은 최소 로그인 화면만 제공하며 운영 화면·신청 데이터는 포함하지 않습니다.
- /ops/, /ops/index.html 및 예시 쿼리도 인증 없이는 로그인 화면으로 이동합니다. JS/CSS 직접 주소도 401로 차단합니다.
- ops/ 원본 폴더를 정적 자산에서 제외하고 server/ops-assets.mjs에 문자열로 번들링합니다. 인증된 Worker만 이를 응답합니다.
- wrangler assets.run_worker_first에는 /ops, /ops/*, /api/ops/*를 지정하여 정적 자산보다 인증 검사를 먼저 수행합니다. 공개 홈페이지 경로는 변경하지 않습니다.
- __Host-elimg_ops 쿠키는 Secure, HttpOnly, SameSite=Strict, Path=/이며 키는 URL·브라우저 localStorage에 저장하지 않습니다.
- 브라우저 뒤로가기로 복원되는 화면은 다시 인증 확인하도록 새로고침합니다. 모든 운영실 응답은 no-store입니다.
- 화면 파일 수정 후 node scripts/build-ops-assets.mjs를 실행합니다. node scripts/build-ops-assets.mjs --check로 동기화를 검사합니다.
- 별도 다운로드용 체험판 HTML은 예시 전용 파일이며 운영 데이터·인증 기능과 연결되지 않습니다.

기술 근거: https://developers.cloudflare.com/workers/static-assets/binding/

## 기존 홈페이지 접수 연결

- 공개 첫 화면의 기존 submitForm은 서버 저장 없이 메일 앱만 열었습니다. 새 contact-intake.js는 /api/lead 저장 응답의 ok와 key를 확인한 뒤에만 완료 문구를 표시합니다.
- 최소 입력과 동의를 확인하고 진행 중 버튼을 잠급니다. 실패·불명확한 응답에서는 완료 표시를 하지 않으며, 자동 재시도로 중복 접수하지 않습니다.
- 기존 Worker의 원본 저장·응답을 유지합니다. 파생 운영실 쓰기가 실패해도 원본 접수는 성공 상태를 유지하며 소유자 연동으로 복구할 수 있습니다.
- 저장된 문의 유형만 기준으로 분류합니다. 자유 서술 내용을 추측하여 의료·비자·선교 분류를 결정하지 않습니다. 중복 유형과 기타 문의는 자동 분류하지 않습니다.
- 원본 키에서 파생한 고정 ID를 사용합니다. 같은 원본 신청의 연동을 반복해도 항목 ID는 변하지 않습니다. 별도로 저장하는 처리 상태(state:)는 재연동이 초기화하지 않습니다.
- 원본 extra 상세 필드는 자동 복사하지 않습니다. 이름·연락처·유형·내용·유입 경로·접수 시각만 연결합니다.
- 원본의 new/contacted/proposal/won/lost는 초기 신규/진행/완료 상태로 매핑됩니다. 이후 원본 상태 변경은 자동 반영하지 않습니다.
- 원본 FEEDBACK 공동 자료함은 그대로 존재합니다. 신규 운영실의 파생 사본만 업무별 저장소로 분리됩니다.
- 원본 삭제는 운영실 사본 삭제로 자동 전파되지 않습니다. 삭제·보관 기간 동기화 정책은 운영 전 별도 검토가 필요합니다.
- 네트워크 오류 후 사용자가 다시 제출하면 서로 다른 원본 키가 생길 수 있습니다. 동일 원본 연동 중복 방지와 사용자 재제출 중복 방지는 구분합니다.
- 실제 자료 자동 복사 및 공개 상담 접수 변경은 배포·활성화 승인을 받은 이후에만 동작합니다.
